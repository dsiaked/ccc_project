# Safe Refactoring Automation

이 저장소에서 기존 동작을 보존하는 리팩토링 작업을 자율적으로 한 번 수행하라.

## 목표

- 사용자 동작, 공개 API, 데이터 형식, 권한 규칙을 변경하지 않는다.
- 중복, 과도하게 긴 함수, 복잡한 조건문, 불명확한 이름, 불필요한 결합 중 하나를 실질적으로 개선한다.
- 한 번의 실행에서는 검토와 검증이 쉬운 작은 리팩토링 하나만 완료한다.

## 시작 절차

1. `git status --short`로 기존 변경 사항을 확인한다.
2. `README.md`, `package.json`, 관련 소스와 테스트를 읽어 저장소 규칙을 파악한다.
3. 코드 검색과 기존 테스트를 근거로 리팩토링 후보를 찾는다.
4. 아래 기준에 따라 위험이 낮고 효과가 분명한 후보 하나를 선택한다.

후보 우선순위:

1. 동일한 로직이 여러 곳에 중복되어 있고 기존 테스트가 있는 코드
2. 순수 함수로 분리할 수 있는 복잡한 계산 또는 조건문
3. 책임이 섞인 긴 함수 중 공개 동작을 유지하며 작은 단위로 분리할 수 있는 코드
4. 의미가 불명확하지만 참조 범위를 확실히 추적할 수 있는 내부 이름

적절한 후보를 찾지 못하면 억지로 수정하지 말고 조사 결과만 보고한다.

## 보호 규칙

- 실행 시작 전에 이미 수정되거나 삭제되거나 새로 생성된 파일은 사용자의 진행 중인 작업으로 간주한다.
- 기존 변경을 되돌리거나 덮어쓰거나 정리하지 않는다.
- 기존 변경 파일을 수정해야만 작업할 수 있다면 다른 후보를 선택한다.
- 관련 없는 파일, 생성 결과물, 잠금 파일, 환경 파일을 수정하지 않는다.
- `.env`, `.env.local`, 비밀 키, 운영 데이터는 읽거나 출력하거나 수정하지 않는다.
- 공개 인터페이스, 라우트, RPC 계약, SQL 함수 시그니처, 데이터베이스 정책, 마이그레이션 순서를 변경하지 않는다.
- 새 의존성을 추가하지 않는다.
- 기능 추가, UI 변경, 성능 최적화, 대규모 파일 이동을 리팩토링과 함께 수행하지 않는다.
- 추상화는 중복이나 복잡도를 실제로 줄이고 이름이 명확해질 때만 추가한다.
- 테스트를 삭제하거나 약화하거나 건너뛰어 통과시키지 않는다.

## 구현 절차

1. 선택한 코드의 현재 동작과 호출 위치를 모두 확인한다.
2. 관련 테스트가 부족하면 현재 동작을 고정하는 좁은 회귀 테스트를 먼저 추가한다.
3. 변경 범위를 가능한 한 적은 파일로 제한해 리팩토링한다.
4. 각 편집 후 diff를 검토해 동작 변경과 관련 없는 변경이 없는지 확인한다.
5. 실패가 발생하면 원인을 조사하고 리팩토링 범위 안에서 해결한다. 기존 동작을 바꾸어 테스트를 맞추지 않는다.

## 검증

변경 범위에 맞춰 좁은 검증부터 실행하고 마지막에 전체 검증을 실행한다.

기본 검증 명령:

```powershell
npm test
npm run lint
npm run build
```

`optimizer/`를 변경한 경우 추가 검증:

```powershell
npm run optimizer:test
```

SQL, Supabase 마이그레이션 또는 Edge Function은 이번 자동 리팩토링 대상으로 선택하지 않는다. 해당 영역에서 개선점을 발견하면 수정하지 말고 보고만 한다.

검증 실패가 기존 작업 트리 변경이나 환경 문제 때문이라면 이를 명확히 구분해 보고한다. 검증을 통과하지 못한 상태에서 변경 범위를 확대하지 않는다.

## 완료 조건

다음 조건을 모두 충족해야 완료로 간주한다.

- 기존 외부 동작이 유지된다.
- 선택한 문제 하나가 명확히 개선된다.
- 변경 사항이 작고 집중되어 있다.
- 관련 테스트와 기본 검증이 통과한다.
- 시작 전에 존재하던 사용자 변경을 훼손하지 않았다.
